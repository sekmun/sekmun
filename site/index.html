Sek-Mun Wong, Sydney

One engineer, an agent loop, and a backlog that keeps running out.

The sprint: 744 points against a 260-point forecast

Sprint 57 was planned at 260 points. The loop closed 744. Scope was written and fed in while the sprint ran, growing from 260 to 799 points, and work kept landing over both weekends.

The loop was already running. What changed on 9 September was cost. DeepSeek V4.1 Flash went live, tokens became cheap enough to leave the loop running unattended, and the 5-hour usage windows stopped dictating when work could happen. The three busiest days of my year followed.

First the constraint was token budget. Remove it, and recent sprints have finished with the backlog empty. The bottleneck is now specification.

Production engineering, with agents in the loop

The sprint chart shows how much got done. This is the part I care about more: how I make software written by agents safe to ship. I deliver production work across TypeScript, Python, PHP and Vue with agents doing most of the implementation, and whatever leverage I get comes from the engineering around the models. That means clear contracts, isolated execution, independent review, and release gates that ask for evidence.

Specifications are the control plane

Everything starts with the specification, because it's the main thing steering the agents. Before work begins, I turn a product decision into a contract: the invariants that must hold, how state moves, who owns which data, what happens when things fail, and what we're deliberately not doing.

When a change crosses services, it becomes a set of linked tickets, one per repository, each with its own branch and pull request. Schema ownership, and how producers and consumers stay compatible, get settled before either side touches code. Accepted time windows, timezones and rule versions are stored as facts when they're decided, so nobody has to reconstruct them later from whatever the settings happen to say.

I use BMAD to draft specifications and to argue with them, but a generated plan never outranks the code that has actually shipped or what's on the live tracker. The best specs are honest about three things: what already exists, what's missing, and what still needs a person to decide.

Multiple models, with verifiable independence

Everything runs through omp.sh, which lets me choose models by role instead of building around a single vendor. Recently that has meant Claude Opus 5, GPT-6.1-Sol and DeepSeek's Flash and Pro models on implementation, with Kimi K2.7-Code, through Kilo, as the independent reviewer. The rule is simple: the reviewer comes from a different model family to the author.

That rule is only worth something if you can check it. Asking for a model by name doesn't guarantee you got it, and a model telling you who it is proves nothing. Providers can fall back silently, and when that happens the author ends up reviewing its own work while looking like a second opinion. So I confirm which model served each response from the routing metadata itself.

These are long-running sessions with tools, rather than one-off prompts. One orchestration archive covering 6 to 21 October holds more than 6,800 assistant messages, before counting subagents, and a recent independent code review ran to 19 turns. Those numbers measure how hard the models worked; they say nothing about features shipped or hours saved. Checkpoints and retained evidence let a session pick up after an interruption without redoing work that's already finished.

Delivery is measured against contracts

I keep story points and model turns in separate books. Points measure the backlog scope that was agreed and accepted; turns measure how much talking, digging and reviewing the models did. Stories get points and epics don't, and scope growth is tracked apart from completed work. The points are my own complexity measure, so they aren't meant to be compared with another team's velocity, and they don't convert into engineer-hours.

Each agent works in its own Git worktree against a throwaway database. Every repository has its own checks: formatting, types, behavioural tests, schema compatibility and smoke tests against a real running system. Here's what a recent backend change had to get through.

I treat review findings as claims to check rather than orders to follow. A real correction gets a focused second review. Cosmetic churn doesn't get to hold up shipping, and neither does a review loop that never ends.

Browser tests run against the real application. I pin the viewport and control transitions so the test can't invent layout bugs of its own, and I keep results from local fault injection clearly apart from proof against live external services.

Edge architecture with a separate batch plane

Durable Objects decide who holds each workspace's ingestion claim, and KV caches configuration. The database schema has one owner, the Laravel migrations, and the TypeScript and Python services work from typed Drizzle and SQLAlchemy mirrors of it. No service can quietly redefine the contract on its own.

At the ingestion boundary, each event's signature is checked and a provisional deduplication claim is taken. The claim only becomes final once the event is safely on the queue, and it's released if enqueueing fails. Live processing and archiving have their own retry and dead-letter paths, so trouble with the archive can never eat into the budget for live work.

Working back through history is a separate job for a Python batch tier. It compacts the raw events in object storage into Iceberg tables partitioned by day and tenant, then shapes them into data the application can use. Reusing embeddings, caching configuration and capping cluster-labelling work keep model costs under control by design, long before a billing alert would notice.

Scale is a design claim until it is measured

I've modelled capacity for 1,000 workspaces and around 1.5 million messages a day. Those are planning numbers, and I don't present them as today's production traffic.

Performance work starts from query plans and realistic fixtures rather than hunches about which index might help. On a synthetic 200,000-row fixture, one hot lookup changed like this:

Hot lookupBeforeAfter
Thread-parent lookup35.7 ms0.10 ms

The fix was a pair of partial and expression indexes that changed the query plan. The obvious indexes didn't help on their own, because both sides of an OR had to become indexable. It's a measured fixture result, and I wouldn't quote it as a production latency guarantee.

Security lives in the boundaries

Requests are authorised per workspace, with PostgreSQL row-level security underneath, tested using a database role that can't bypass it. The privileged ingest and batch services sit behind a separately documented trust boundary, so I don't claim row-level security protects everything. Alongside that there are:

  • raw-body HMAC verification with bounded replay windows
  • single-use OAuth state bound to the user
  • encrypted credentials kept out of normal serialisation
  • explicit channel-access scopes and privacy classification
  • audited operator sessions that expire, with revocation that's verified.

One small design choice I'm fond of: access is always all, assigned or none. It's never an empty list, because an empty list is exactly the kind of value that switches filtering off by accident. The testing matters as much as the mechanism here. If your tenant-isolation tests run as a database superuser, they can't prove anything.

A green pipeline is not the end of the work

Merging, releasing, deploying and switching a feature on are four separate decisions. Coordinated releases apply additive schema changes before the services that depend on them, go through UAT before production, pin source versions and keep evidence for rollback. API and batch container images are promoted exactly as tested, and Workers that haven't changed aren't redeployed.

After a deploy I check what's actually running: the version, its health and its configuration. A green workflow tells me the pipeline finished, which isn't the same as knowing what's live. Turning a feature on can be its own rolling configuration change, so accepted code doesn't need rebuilding and existing customers aren't moved onto new behaviour without choosing it.

A recent acceptance test for a scheduled workflow shows why this matters. The business outcome is committed first, and delivery is recorded separately for each destination. In the test, one destination accepted the delivery and the external service deliberately rejected the other. The stored outcome stayed as it was, the interface showed a partial delivery, and the one-off job didn't create a successor. When we can't tell whether a send went through, it stays marked as uncertain; it's never reported as a success or blindly retried.

The agents do the implementation. I'm accountable for the contracts, the architecture, the evidence, and the call to ship.
