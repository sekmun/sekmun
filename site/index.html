One engineer, an agent loop, and a backlog that keeps running out.

The sprint: 744 points against a 260-point forecast

Sprint 57 was planned at 260 points. The loop closed 744. Scope was written and fed in while the sprint ran, growing from 260 to 799 points, and work kept landing over both weekends.

The loop was already running. What changed on 9 September was cost. DeepSeek V4.1 Flash went live, tokens became cheap enough to leave the loop running unattended, and the 5-hour usage windows stopped dictating when work could happen. The three busiest days of my year followed.

First the constraint was token budget. Remove it, and recent sprints have finished with the backlog empty. The bottleneck is now specification.

Production engineering, with agents in the loop

Throughput is the easy part to show. This is how I make agent-written software safe to ship. I use AI agents to deliver production software across TypeScript, Python, PHP and Vue. The leverage comes from the engineering around the models: precise contracts, isolated execution, independent review and evidence-based release gates.

Specifications are the control plane

I turn product decisions into implementation contracts: invariants, state transitions, data ownership, failure behaviour and explicit non-goals.

Cross-service changes become linked, repository-scoped tickets, with one branch and pull request per repository. Schema ownership and producer/consumer compatibility are settled before either side changes. Accepted time windows, timezones and rule versions are persisted facts, not reconstructed later from current settings.

BMAD helps draft and challenge specifications, but generated plans don't outrank shipped code or the live tracker. A useful specification distinguishes what already exists, what is missing and what still needs a human decision.

Multiple models, with verifiable independence

I use omp.sh as a model-agnostic orchestration harness. Recent captured runs include Claude Opus 5, GPT-6.1-Sol and DeepSeek Flash and Pro variants, with Kimi K2.7-Code through Kilo used for independent review.

Models are selected by role rather than making one vendor the architecture. Repository-scoped agents implement changes; a model from a different family reviews them.

I verify which model actually served each response from native routing metadata. A requested model name, or a model describing itself, is not proof. Silent fallback can otherwise make the author review its own work while appearing to provide an independent opinion.

These are persistent, tool-using sessions, not single prompts. One orchestration archive spanning 6–21 October contains over 6,800 assistant messages, excluding separate subagent sessions. A recent independent code review ran to 19 recorded turns. Those figures describe model interaction and instrumentation, not features delivered or human hours saved. Checkpoints, source identities and retained evidence let work resume after interruptions without blindly restarting completed implementation.

Delivery is measured against contracts

Story points and model turns are separate ledgers. Points describe accepted backlog scope; turns describe model interaction, investigation and review. Stories are pointed, epics stay unpointed, and scope growth is tracked separately from completed work. Points are an internal complexity measure, not a comparison with another team's velocity or a conversion into engineer-hours.

Agents work in isolated Git worktrees and disposable databases. Repository-specific checks cover formatting, types, behavioural tests, schema compatibility and real runtime smoke checks.

Review findings are claims to validate, not instructions to obey. Material corrections get a focused re-review; cosmetic churn and endless review loops don't become a substitute for shipping.

Browser verification exercises the real application. Viewports are asserted and transitions controlled so the measuring instrument doesn't invent layout bugs. Local fault injection and live external-service proof are labelled separately.

Edge architecture with a separate batch plane

Durable Objects coordinate per-workspace ingestion claims; KV caches configuration. Eloquent-owned migrations and typed Drizzle and SQLAlchemy mirrors stop services independently redefining the same database contract.

The ingestion boundary validates signed events and coordinates provisional deduplication claims. A claim is confirmed only after enqueue succeeds, and released if enqueue fails. Live processing and archival have separate retry and dead-letter paths, so archive problems can't consume the live processing budget.

Retrospective processing runs in a separate Python batch tier. Raw object-storage events are compacted into day-and-tenant-partitioned Iceberg tables, then transformed into application-facing data. Embedding reuse, cached configuration and bounded cluster-labelling work make model cost an architectural concern, not just a billing alert.

Scale is a design claim until it is measured

Capacity modelling has covered 1,000 workspaces and roughly 1.5 million messages a day. Those are planning assumptions, not claims about current production traffic.

Performance work uses query plans and representative fixtures rather than adding indexes by intuition. A recorded synthetic benchmark used a 200,000-row fixture:

Partial and expression indexes changed the query plan. The obvious indexes weren't enough: both branches of an OR expression had to become indexable. This is a documented fixture result, not a production latency SLA.

Security lives in the boundaries

The request tier combines workspace-scoped authorisation with PostgreSQL row-level security, tested under a non-bypass database role. Privileged ingest and batch services have a separately documented trust boundary; I don't describe RLS as universal protection. Other controls include:

  • Raw-body HMAC verification and bounded replay windows.
  • Single-use, user-bound OAuth state.
  • Encrypted credentials excluded from normal serialisation.
  • Explicit channel-access scopes and privacy classification.
  • Audited, expiring operator sessions with verified revocation.

Access is represented as all, assigned or none, never an ambiguous empty array that can accidentally disable filtering. The verification matters as much as the mechanism: a test running as a database superuser can't prove that tenant isolation works.

A green pipeline is not the end of the work

Merge, release, deployment and activation are separate decisions. Coordinated releases apply additive schema changes before compatible consumers, promote through UAT before production, pin source identities and retain rollback evidence. API and batch container images are promoted unchanged; path filtering avoids redeploying unchanged Workers.

I check the running version, health and applied configuration rather than treating a successful workflow as proof of runtime state. Feature activation can be a separate rolling configuration change, without rebuilding accepted code or opting existing customers into new behaviour.

A recent scheduled-workflow acceptance case made that distinction concrete: commit the business outcome first, then record delivery independently for each destination. One destination delivered and another was deliberately rejected by the external service. The stored outcome stayed unchanged, the UI reported partial delivery, and the one-off created no successor. Ambiguous sends stay uncertain rather than being reported as success or blindly replayed.

The agents do the implementation. I remain accountable for the contracts, architecture, evidence and authority to ship.
