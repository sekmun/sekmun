Loop engineering is still engineering. Here are the receipts.

I build production software with AI agents running in a loop: they plan, specify, build, verify, ship and run it, and the models do most of the typing. None of it is vibe coding. The tools are new; the principles are old. What I've been working out this year is how to wrap proper engineering discipline around the latest harnesses and models, so the loop can run on its own and still be trusted with production.

Where I am with it

Loop engineering comes in stages, and each one moves the bottleneck somewhere new. Most of the skill is noticing where it went.

  1. AssistedA model helps and I drive every step. The constraint is me.
  2. LoopedAgents implement inside gates I design: contracts go in, evidence comes out. The constraint becomes the token budget, and the 5-hour usage windows that decide when work can happen.
  3. UnattendedOn 9 September DeepSeek V4.1 Flash went live, and tokens became cheap enough to leave loops running overnight and through weekends. Sprint 57 was already under way. It finished at 744 points against a 260-point forecast.
  4. Specification-boundRecent sprints end with the backlog empty. The constraint has moved upstream, to writing contracts good enough for a loop to execute without me.

The loop, stage by stage

Every stage of the loop is a discipline I've practised for a long time, rebuilt so that agents can work inside it. Speed is the side effect. The craft is in making each stage hold when nobody is watching.

Plan Scrum, delivery management and BMAD

Running scrum for a team of agents is still running scrum. Work is planned in two-week sprints on a ClickUp board, stories get points and epics don't, and scope that arrives mid-sprint is tracked apart from the work that's done, so a sprint that grows from 260 to 799 points is visible as exactly that.

I keep story points and model turns in separate books. Points measure the scope that was agreed and accepted; turns measure how hard the models worked. The points are my own complexity measure, so they aren't a comparison with anyone else's velocity, and they don't convert into engineer-hours.

I use BMAD to draft plans and to argue with them, but a generated plan never outranks the code that has actually shipped or what's on the live tracker. A good plan is honest about three things: what already exists, what's missing, and what still needs a person to decide.

Specify Contracts an agent can be held to

The specification is the main thing steering the agents, so it gets the most care. A product decision becomes a contract: the invariants that must hold, how state moves, who owns which data, what happens when things fail, and what we're deliberately not doing.

A change that crosses services becomes a set of linked tickets, one per repository, each with its own branch and pull request. Schema ownership and producer/consumer compatibility are settled before either side touches code. Time windows, timezones and rule versions are stored as facts when they're decided, so nobody reconstructs them later from whatever the settings happen to say.

Build Multi-model, multi-language, isolated

The platform spans Laravel with Octane and Vue, Python for the API and batch tiers, and TypeScript on Cloudflare Workers and Node.js. The database schema has a single owner, the Laravel migrations, and the TypeScript and Python services work from typed Drizzle and SQLAlchemy mirrors of it, so no service can quietly redefine the contract.

Each agent works in its own Git worktree against a throwaway database, so parallel agents can't trample each other and a bad run costs nothing to discard. Checkpoints and retained evidence let a session resume after an interruption without redoing finished work.

Everything runs through omp.sh, and I chose it on evidence. Composio's August 2026 comparison ran the same model, Kimi K3, through eight harnesses, including Claude Code, Codex and OpenCode, on 25 real business-app tasks, scoring each by the final state of the apps. Oh My Pi, the project behind omp.sh, completed 22 of the 25, the best of the eight, at an estimated 52 US cents per successful task.

Models are chosen by role rather than by loyalty. Recent runs have used Claude Opus 5, GPT-6.1-Sol and DeepSeek's Flash and Pro models for implementation, and Kimi K2.7-Code, through Kilo, for independent review. DeepSeek V4.1 Flash changed the economics: once a loop is cheap enough to run unattended, it stops being a session and becomes infrastructure. One orchestration archive from 6 to 21 October holds more than 6,800 assistant messages, before counting subagents.

Verify Unit coverage, front-end tests, independent review

Tests are what let me trust code I didn't type. Coverage is reported on every build and badged at the top of each repository: 80.71% on the Laravel core and 95.39% on the Python services. I don't chase 100%. Coverage tells me where nobody has checked yet, and the tests tell me the code does what the contract says.

Front-end behaviour is verified in a real browser against the real application. Viewports are pinned and transitions controlled so the test can't invent layout bugs of its own, and results from local fault injection are kept clearly apart from proof against live external services. Each repository adds its own gates on top: formatting, types, schema compatibility and smoke tests against a running system. Here's what one recent backend change had to get through.

Review comes from a model in a different family to the author, and I check that it really was. Asking for a model by name doesn't guarantee you got it, and providers can fall back silently, which would leave the author reviewing its own work while looking like a second opinion. So I confirm which model served each response from the routing metadata. Findings are treated as claims to check, not orders: a real correction gets a focused re-review, and cosmetic churn doesn't get to hold up shipping.

Ship Infrastructure as code, GitHub Actions, gated releases

The whole platform is infrastructure as code. Environments, configuration and pipelines live in the repositories alongside the application, and every build, test, release and deploy runs in GitHub Actions. That matters more with agents than without them: an agent can read, change and review the infrastructure exactly as it does the application, through the same pull requests and checks.

Merging, releasing, deploying and switching a feature on are four separate decisions. Additive schema changes go out before the services that depend on them, releases pass through UAT before production, source versions are pinned and rollback evidence is kept. Container images are promoted exactly as tested, and Workers that haven't changed aren't redeployed. A feature can be switched on as its own rolling configuration change, without rebuilding accepted code or moving existing customers onto new behaviour.

A recent acceptance test for a scheduled workflow shows why the separation matters. The business outcome is committed first, and delivery is recorded separately for each destination. In the test, one destination accepted and the external service deliberately rejected the other. The stored outcome stayed put, the interface showed a partial delivery, and the one-off job didn't create a successor. When we can't tell whether a send went through, it stays marked as uncertain; it's never reported as a success or blindly retried.

Run Edge architecture, telemetry, security, scale

Signed events land on Cloudflare's edge. Each signature is checked and a provisional deduplication claim is taken, coordinated per workspace by Durable Objects; the claim only becomes final once the event is safely queued, and it's released if queuing fails. Live processing and archiving have separate retry and dead-letter paths, so trouble with the archive never eats into the live budget. A Python batch tier compacts the raw archive in R2 into Iceberg tables partitioned by day and tenant, and reuses embeddings and caches configuration so model cost is controlled by design rather than by a billing alert.

Telemetry covers the loop as well as the product. After every deploy I check what's actually running, its version, health and applied configuration, because a green workflow only proves the pipeline finished. And every agent session is archived with the model that really served each response, so I can audit who wrote and who reviewed anything that reached production.

Security lives in the boundaries. Requests are authorised per workspace with PostgreSQL row-level security underneath, tested under a role that can't bypass it, because a tenant-isolation test running as a superuser proves nothing. The privileged ingest and batch services sit behind their own documented trust boundary. Alongside that: raw-body HMAC verification with bounded replay windows, single-use OAuth state bound to the user, encrypted credentials kept out of normal serialisation, explicit channel scopes, and audited operator sessions that expire. Access is always all, assigned or none; never an empty list that can switch filtering off by accident.

The platform is designed for 1,000 workspaces and around 1.5 million messages a day, and I treat that as a design target until production proves it. Performance work starts from query plans and realistic fixtures, not hunches. On a 200,000-row fixture, partial and expression indexes took one hot lookup from 35.7 ms to 0.10 ms, once both sides of an OR had been made indexable.
